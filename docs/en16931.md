# EN 16931 totals in plain JSON Schema

EN 16931, the European standard for electronic invoices, states its document totals as sums and differences of two-decimal amounts. Schema Calc compiles seven of those rules, BR-CO-10 to BR-CO-16, into one standard JSON Schema, which a stock validator runs on a flat JSON form of an invoice. This page compares the schema's verdicts with the official Schematron's: on every example invoice published with the official validation artefacts, and on copies of them with one or more totals changed by one cent.

**On 475 invoices the verdicts are the same, rule by rule, for all but six.** All six are CII invoices on which the CII Schematron is more lenient than the rule it checks. The schema is 9.6 MB, most of it for adding up 20 signed line amounts. Python `jsonschema` runs it with its default options; Ajv runs it once its resources are added one at a time, as the playground does.

## The rules

| Rule | What must hold | In the contract |
|---|---|---|
| BR-CO-10 | Sum of invoice line net amounts (BT-106) = Σ invoice line net amount (BT-131) | `lineNetTotal = sum(lines.netAmount)` |
| BR-CO-11 | Sum of allowances on document level (BT-107) = Σ document level allowance amount (BT-92) | `allowanceTotal = sum(allowances.amount)` |
| BR-CO-12 | Sum of charges on document level (BT-108) = Σ document level charge amount (BT-99) | `chargeTotal = sum(charges.amount)` |
| BR-CO-13 | Invoice total without VAT (BT-109) = Σ BT-131 − document allowances (BT-107) + document charges (BT-108) | `totalWithoutVat = lineNetTotal - allowanceTotal + chargeTotal` |
| BR-CO-14 | Invoice total VAT amount (BT-110) = Σ VAT category tax amount (BT-117) | `vatTotal = sum(vatBreakdown.taxAmount)` |
| BR-CO-15 | Invoice total with VAT (BT-112) = BT-109 + invoice total VAT amount (BT-110) | `totalWithVat = totalWithoutVat + vatTotal` |
| BR-CO-16 | Amount due for payment (BT-115) = BT-112 − paid amount (BT-113) + rounding amount (BT-114) | `amountDue = totalWithVat - paidAmount + roundingAmount` |

Four details come from the official Schematron rather than from a summary of the rules:

- **BR-CO-13 uses BT-106**, the invoice's own sum of line net amounts, rather than adding the lines again. Where BR-CO-10 holds the two are the same; where it fails, only BR-CO-10 reports it, in both the Schematron and the schema.
- **BR-CO-16 includes the rounding amount**, BT-114, which can be negative.
- **A missing total is checked case by case.** BR-CO-11 and BR-CO-12 accept a missing BT-107 or BT-108 only when the invoice has no allowances or charges. BR-CO-14 checks BT-110 only where it is given, and in UBL only for a VAT total that has a breakdown. BR-CO-13, -15 and -16 count a missing amount as zero.
- **Every rule rounds to the cent.** All amounts in these rules have at most two decimals, so the rounding never changes a result, and the schema checks exact equality.

## The JSON form

[contract.json](../en16931/contract.json) declares the form and the seven rules:

| JSON | Business term | UBL | CII | |
|---|---|---|---|---|
| `lineNetTotal` | BT-106 | `LegalMonetaryTotal/LineExtensionAmount` | `LineTotalAmount` | required |
| `allowanceTotal` | BT-107 | `LegalMonetaryTotal/AllowanceTotalAmount` | `AllowanceTotalAmount` | optional |
| `chargeTotal` | BT-108 | `LegalMonetaryTotal/ChargeTotalAmount` | `ChargeTotalAmount` | optional |
| `totalWithoutVat` | BT-109 | `LegalMonetaryTotal/TaxExclusiveAmount` | `TaxBasisTotalAmount` | required |
| `vatTotal` | BT-110 | `TaxTotal/TaxAmount` in the document currency | `TaxTotalAmount` in the invoice currency | optional |
| `totalWithVat` | BT-112 | `LegalMonetaryTotal/TaxInclusiveAmount` | `GrandTotalAmount` | required |
| `paidAmount` | BT-113 | `LegalMonetaryTotal/PrepaidAmount` | `TotalPrepaidAmount` | optional |
| `roundingAmount` | BT-114 | `LegalMonetaryTotal/PayableRoundingAmount` | `RoundingAmount` | optional |
| `amountDue` | BT-115 | `LegalMonetaryTotal/PayableAmount` | `DuePayableAmount` | required |
| `lines[].netAmount` | BT-131 | `InvoiceLine/LineExtensionAmount` | `SpecifiedTradeSettlementLineMonetarySummation/LineTotalAmount` | each line |
| `allowances[].amount` | BT-92 | `AllowanceCharge/Amount` with `ChargeIndicator` false | `SpecifiedTradeAllowanceCharge/ActualAmount` with `ChargeIndicator` false | each allowance |
| `charges[].amount` | BT-99 | `AllowanceCharge/Amount` with `ChargeIndicator` true | `SpecifiedTradeAllowanceCharge/ActualAmount` with `ChargeIndicator` true | each charge |
| `vatBreakdown[].taxAmount` | BT-117 | `TaxSubtotal/TaxAmount` of that VAT total | `ApplicableTradeTax/CalculatedAmount` | each VAT category |

The CII elements are in the header or line trade settlement summation. Each amount is a decimal string with exactly two fractional digits and an optional minus sign, such as `"-25.00"`, with at most six integer digits. An absent optional amount counts as zero. The four lists are always present, and may be empty: an invoice has at most 20 lines and at most five allowances, charges and VAT categories each. An item may carry other properties, such as a line's `id`, an allowance's reason code or a VAT category's code; only its amount is checked. The second UBL example becomes:

```json
{
  "lineNetTotal": "1436.50", "allowanceTotal": "100.00", "chargeTotal": "100.00",
  "totalWithoutVat": "1436.50", "vatTotal": "365.28", "totalWithVat": "1801.78",
  "paidAmount": "1000.00", "amountDue": "801.78",
  "lines": [
    { "id": "1", "netAmount": "1273.00" }, { "id": "2", "netAmount": "-3.96" },
    { "id": "3", "netAmount": "4.96" }, { "id": "4", "netAmount": "-25.00" },
    { "id": "5", "netAmount": "187.50" }
  ],
  "allowances": [{ "reason": "88", "amount": "100.00" }],
  "charges": [{ "amount": "100.00" }],
  "vatBreakdown": [
    { "category": "S", "taxAmount": "365.13" }, { "category": "S", "taxAmount": "0.15" },
    { "category": "E", "taxAmount": "0.00" }
  ]
}
```

[convert.py](../en16931/convert.py) writes this form from UBL or CII XML using only Python's standard library. It copies each business term and rewrites its decimal with two fractional digits, so `130` becomes `"130.00"`; it never computes a total. An allowance or charge is read as the Schematron reads its `ChargeIndicator`, so `0` and `1` count as false and true. A value that two digits cannot hold exactly, or one with more than six integer digits, is copied unchanged, so the schema rejects its format.

## Agreement

The official artefacts are release [validation-1.3.17](https://github.com/ConnectingEurope/eInvoicing-EN16931/releases/tag/validation-1.3.17), whose Schematron is published compiled to XSLT. Saxon-HE runs it on each XML invoice. The JSON form of the same invoice is checked by the schema for all seven rules and by a schema for each rule alone, all in Ajv.

Besides each unchanged example, the comparison adds one cent to each total the invoice has, one at a time, and to the first item of each list that has one. Six further changes keep one rule true while breaking another: the first line together with BT-106, which breaks only BR-CO-13; the first allowance with BT-107, and the first charge with BT-108, which also break only BR-CO-13; the first VAT category with BT-110, which breaks only BR-CO-15; BT-112 together with BT-115, which breaks only BR-CO-15; and BT-109, BT-112 and BT-115 together, which breaks only BR-CO-13. The verdicts are the same when the seven rules the Schematron reports as failed are exactly those whose schemas reject the JSON, and the schema for all seven rejects exactly when the Schematron reports any of them.

**The six different verdicts** have two causes, both in the CII Schematron:

- **BR-CO-15 accepts BT-112 = BT-109 whatever BT-110 is.** The CII Schematron accepts an invoice when BT-112 = BT-109 + BT-110, or else when BT-112 = BT-109. On `CII-BR-CO-10-RoundingIssue.xml` and `CII_business_example_Z.xml`, whose VAT total is zero, raising BT-110 by a cent, alone or together with the VAT breakdown, therefore passes BR-CO-15: four verdicts. The rule's text and the UBL Schematron do not accept them, and neither does the schema.
- **BR-CO-14 is not checked without BT-110.** The CII Schematron attaches BR-CO-14 to the VAT total element, so an invoice without one has nothing to check. `CII_example7.xml` and `XRechnung-O.xml` are not subject to VAT and give no BT-110; raising their VAT category's tax amount from zero to a cent passes BR-CO-14 there: two verdicts. The schema counts an absent BT-110 as zero, as both Schematrons do in BR-CO-15, and rejects them. (The Schematron rejects these invoices too, under BR-O-09, which requires a tax amount of zero for that category.)

Every other verdict agrees, for each rule separately and for all seven together. Python `jsonschema` with its default options gives the same verdicts as Ajv on every invoice.

The times compare unlike work: the Schematron checks all of EN 16931's rules, and the schema seven. Preparing the schema is the expensive part. Adding its resources to Ajv bottom-up, as the playground does ([ajv-validator.mjs](../src/ajv-validator.mjs)), takes seconds; Ajv's own `compile` takes minutes, against well under a second for Saxon to compile the XSLT. Python `jsonschema` prepares lazily and pays per invoice instead.

## Limits

- **At most 20 lines and six integer digits.** BR-CO-10 adds up every line in a fixed decision graph. In each column it reads how many lines have each digit, and how many of those are negative, with `contains`, `minContains` and `maxContains` ([design.md](design.md#domain)); the schema grows faster than the number of lines, and linearly with the number of digits. BR-CO-11, -12 and -14 add up at most five items each, at about 0.7 MB apiece; the three rules without a list take 548 kB, and the six without BR-CO-10 take 2.7 MB.
- **Close to the validators' stack limits.** Python `jsonschema` needs about 475 stack frames for a 20-line invoice, within its default of 1,000; reading every line position in turn needed over 1,700. Ajv's own `compile` turns a document this size into functions too large for Node's default stack: with default options it compiles in about three and a half minutes and then overflows while validating, and with `inlineRefs: false` some validations overflow. Adding the resources to Ajv bottom-up, each compiled on its own ([ajv-validator.mjs](../src/ajv-validator.mjs)), avoids both.
- **Syntax bindings differ from the rules.** The schema follows the rules as written, with an absent amount counted as zero. The Schematrons add or drop a condition in four places:
  - The UBL Schematron's BR-CO-15 also requires exactly one VAT total in the document currency. The form has one optional `vatTotal`, and the converter writes two as a list, which the schema rejects.
  - The CII Schematron's BR-CO-15 also accepts BT-112 = BT-109 whatever BT-110 is. The schema rejects that.
  - BR-CO-14 checks nothing in CII when BT-110 is absent, nor in UBL for a VAT total without a breakdown. The schema requires the breakdown to add up to BT-110, or to zero without it.
  - Both Schematrons' BR-CO-11 and BR-CO-12 reject an absent BT-107 or BT-108 when there are allowances or charges, even if those add up to zero. The schema accepts that.

  Only the second and third occur among the examples and their changes.
- **Products are out of reach.** BR-CO-17 requires each VAT category's tax amount to equal its taxable amount times its rate, within a cent, and a line's net amount is its quantity times its price. A product of two fields is not a linear relation. The compiler reads digits column by column with a bounded carry, and multiplying two eight-digit numbers that way would need state for every partial product. A rate drawn from a short fixed list could be handled by one linear constraint per rate, chosen by the rate's value, but that is not built.

## Reproduce it

```sh
en16931/fetch.sh              # official artefacts at validation-1.3.17, and Saxon-HE 12.5
node en16931/run.mjs --python # needs Python 3 and a JDK; --write updates this page
```
